# Video to Markdown Side Panel 2.0 原型评审

- 评审日期：2026-07-15
- 评审对象：P01–P12、Flow Overview、0.2.0 交互升级需求
- 原型基准：Chrome Side Panel，380 × 760px
- 评审结论：有条件通过，可以进入技术实施计划阶段
- 关联需求：[Video to Markdown 产品与技术设计规格](../specs/2026-07-12-video-to-markdown-extension-design.md#20-side-panel-20-交互升级概述)
- 原型索引：[Side Panel 2.0 原型](../../prototypes/side-panel-v2/README.md)

## 1. 评审范围与方法

本次评审从以下五个维度检查原型：

1. 需求覆盖：是否覆盖首次使用、准备、配置、生成、结果和恢复流程。
2. 任务闭环：用户是否始终知道当前状态、下一步操作和已有结果是否安全。
3. 视觉层级：页面是否只有一个最高权重主操作，信息密度是否适合 Side Panel。
4. 可访问性与响应式：文字、对比度、焦点、键盘和 320px 宽度是否可落地。
5. 技术可实现性：原型是否可以映射到现有 React、WXT、Service Worker 和任务编排结构。

评审同时对照了当前实现中的 `AppPhase`、`TaskState`、模型消息协议、模型配置、本地偏好和 Markdown 渲染逻辑，以避免原型提出无法安全落地的交互。

## 2. 总体结论

原型已经完成从“程序状态页面”到“用户任务流程”的主要升级，主流程明确：

```text
识别当前视频 → 配置生成方式 → 可视化生成与导出
```

P03、P04、P07、P08、P09 和 P10 是本轮质量最高的页面：模式选择和模型依赖关系清楚；生成过程区分了“等待首段”和“已有增量正文”；部分失败保留成功内容；结果页具有明确的阅读与导出层级。

原型不需要推倒重画，可以作为开发基线。但在正式实现前必须关闭 5 个高优先级缺口，并在实现阶段落实 6 个中优先级改进。评审结论因此为“有条件通过”。

## 4. 做得好的部分

### 4.1 任务主线清晰

Flow Overview 将 12 个状态归入环境识别、生成配置、生成与导出三段，符合用户心智。用户不再需要理解 Content Script、模型请求或分块处理等内部概念。

### 4.2 模型按需配置成立

P03 与 P04 清楚表达：

- 中文字幕高保真可以本地处理。
- 英文高保真和 AI 精炼需要模型。
- 缺少模型时，主按钮变为“配置模型并继续”。

这比当前“没有配置就完全不读取视频”的实现更合理，也是 0.2.0 最重要的产品决策之一。

### 4.3 黑盒等待得到实质改善

P07 和 P08 没有只使用旋转图标，而是分别展示：

- 字幕数量。
- 自然段数量。
- 当前分块。
- 模型连接或接收活动。
- 已等待时间。
- 已验证的增量正文。
- 自动滚动状态。
- 停止后保留成功内容。

该交互可以直接映射到任务事件模型，具有技术可实现性。

### 4.4 操作层级明显改善

准备、设置、生成、部分完成、结果和错误页面基本都只有一个实心主按钮。删除配置、重新尝试、下载和重新生成等操作被降为次级或危险操作，解决了当前三个紫色按钮并排的问题。

### 4.5 结果默认可读

P10 默认展示领域对象渲染后的阅读预览，P11 再切换到 Markdown 源码，符合“阅读优先、源码辅助”的产品目标。实现时不需要把模型文本作为 HTML 注入，可以继续保持安全边界。

## 5. 必须在开发前关闭的问题

### R-P0-01：缺少初始加载和无字幕状态

- 级别：必须修正
- 影响：首次打开、页面检测、字幕适配
- 当前情况：P01 覆盖不支持页面，P02 覆盖需要刷新，但没有单独表达“正在检测”和“视频存在但没有字幕”。
- 风险：实现时容易继续把 `NO_SUBTITLE`、脚本未注入和平台异常混成同一个错误页面。
- 处理决定：不必增加大型独立页面，但必须新增可复用的 `LoadingState` 和 `NoSubtitleState`，并分别测试。

### R-P0-02：P06 将测试中和成功同时展示

- 级别：必须修正
- 影响：模型连接测试
- 当前情况：P06 作为设计参考同时画出了测试中卡片和成功卡片。
- 风险：正式实现如果照搬，会让用户误以为测试尚未结束但又已经成功。
- 处理决定：实现中拆成 `testing`、`success`、`failed` 三个互斥状态；原型画板只作为状态样式参考。

### R-P0-03：缺少活动标签页切换确认

- 级别：必须修正
- 影响：生成中切换标签页或切换视频
- 当前情况：需求规定任务进行中不得静默切换，但 P01–P12 没有确认交互。
- 风险：任务标题、字幕来源和结果可能与用户当前看到的视频不一致。
- 处理决定：实现一个非独立全屏的确认 Sheet，提供“继续当前任务”和“停止并加载新视频”。

### R-P0-04：辅助文字尺寸下限不足

- 级别：必须修正
- 影响：全部画板，尤其设置、生成状态和错误详情
- 当前情况：原型中存在 9–11px 的说明文字。
- 风险：在高分屏 Side Panel 或系统缩放下可读性不足，不利于 WCAG AA 落地。
- 处理决定：实现时正文不低于 13px，辅助说明不低于 12px，极少量代码/时间标签不低于 11px；不直接复制原型像素字号。

### R-P0-05：320px 下服务商选择需要重排

- 级别：必须修正
- 影响：P05 模型设置
- 当前情况：DeepSeek、OpenAI、OpenRouter、自定义在 380px 下可以横排，但 320px 下会拥挤。
- 风险：文字压缩、点击目标过小或产生横向滚动。
- 处理决定：宽度小于 360px 时改为 2 × 2 网格；服务商选项点击高度不低于 40px。

## 6. 实现阶段改进项

### R-P1-01：强化 P01 主操作

P01 的“重新检测当前页面”使用了描边按钮。实现时应在用户已打开视频但尚未重新检测的场景使用实心主按钮；纯不支持页面可以保留描边按钮，并把重点放在如何打开受支持视频。

### R-P1-02：明确自动滚动交互

P08 的“自动滚动已开启”需要实现为可操作控件。用户向上滚动后自动暂停，并出现“回到最新”；只有用户回到底部或主动恢复后才重新自动滚动。

### R-P1-03：定义结果页更多菜单

P10 顶部更多菜单至少包含：重新生成、返回准备设置。不得把删除内容或危险操作混入同一层级。

### R-P1-04：部分导出必须标记不完整

P09 的“导出当前结果”需要在 Markdown 元信息区写入明显的不完整标记和失败分块数量，文件名可追加 `-partial`，避免用户把不完整内容误认为最终稿。

### R-P1-05：模型配置需要迁移与状态记录

P05/P06 需要记录服务商预设、最近测试状态和响应耗时，同时兼容已经保存的旧版 `apiKey/baseUrl/model/contextWindow` 配置，不能要求用户重新输入密钥。

### R-P1-06：设置页返回时保留任务上下文

从 P04 进入 P05，再测试成功返回后，应恢复原视频、字幕和模式选择，而不是重新回到初始化页面或丢失已选字幕轨道。

## 8. 可访问性检查清单

- 模式卡由可聚焦的 radio 组实现，不能只靠外框和圆点表示选中。
- 图标按钮必须提供 `aria-label` 和可见焦点。
- 主要点击目标高度不低于 40px。
- 正文不低于 13px，辅助说明不低于 12px。
- 进度变化使用 `aria-live="polite"`，错误使用 `role="alert"`。
- 颜色之外同时使用文字、图标或边框表达成功、警告和错误。
- 320px 宽度下检查 `documentElement.scrollWidth <= clientWidth`。
- 遵循 `prefers-reduced-motion`，不依赖旋转动画表达唯一状态。

## 9. 技术可实现性结论

### 可以直接复用

- 当前字幕适配器、标准化、段落恢复和分块逻辑。
- 当前失败分块保存和 `retryFailed()` 基础能力。
- 当前 Markdown 领域对象和时间戳渲染逻辑。
- 当前模型配置本地存储与可选来源权限。

### 必须重构

- `App.tsx`：从单一 `AppPhase` 条件渲染升级为产品状态和子页面导航。
- `TaskState`：增加阶段键、任务指标、流活动、增量预览和失败详情。
- 模型通信：长任务从单次 `sendMessage()` 升级为 `chrome.runtime.Port`。
- `OpenAICompatibleProvider`：增加 SSE 流解析与非流式降级。
- 结果界面：从 `<pre>` 改为领域对象阅读预览和 Markdown 源码切换。
- CSS：增加设计变量、固定操作栏、滚动区和 320px 响应式规则。

### 风险判断

- Level 1 分块增量输出风险低，应先交付。
- Level 2 Token 流式风险中等，主要风险是提供商 SSE 差异和结构化 JSON 不适合直接展示。
- NDJSON 只能作为可读增量协议，必须保留完整 JSON/非流式降级路径。
- 不建议在同一个提交中同时重构 UI、任务状态和模型传输，应按实施计划分阶段合并。

## 10. 评审决议

原型有条件通过，允许进入技术实施计划和开发阶段。开发必须遵循以下门槛：

1. 先补产品状态与 UI 基础，再接入流式通信。
2. 先完成 Level 1 分块增量，再实现 Level 2 Token 流式。
3. R-P0-01 至 R-P0-05 必须在 0.2.0 发布前关闭。
4. 现有字幕提取修复和测试不得因 UI 重构回退。
5. 每个阶段独立通过类型检查、单元测试和相关端到端测试。
